# Development log - 2026-09

## 2026-09-05 - Repository scripts and tests move to TypeScript

**Result**

- All 22 repository-owned Node.js entrypoints under `scripts/` and `test/`
  now use directly executable `.ts` files; the workspace no longer carries
  `.js`, `.mjs`, or `.cjs` source files.
- `npm run typecheck` now checks both the strict production package program and
  a separate tools/test program. A repository contract prevents JavaScript
  entrypoints from returning and verifies that scripts and tests stay in the
  TypeScript program.

**Why / context**

- Node.js 24 already executes the workspace's erasable package TypeScript, so
  retaining a second source format for release checks and tests added no runtime
  compatibility value. Converging the repository on `.ts` makes import paths,
  editor tooling, and compiler coverage consistent without adding a build step.
- Runtime contract tests deliberately construct malformed values and dynamic
  owner stand-ins. `tsconfig.tools.json` keeps those fixtures typechecked with
  explicit boundary casts while `tsconfig.json` continues to enforce the full
  strict contract for shipped package sources.
- Three `.mjs` strings remain intentionally: they resolve the exact external
  runtime-kit checkout's compiled test helper and are not repository-owned
  entrypoints.

**Evidence**

- The repository contract first failed while listing all 22 legacy entrypoints,
  then passed after the conversion.
- `npm test`, `npm run typecheck`, manifest-only compatibility validation,
  reproducible-package verification, and package dry-run all pass on the
  repository-pinned Node.js runtime.

**Links**

- `README.md`, `CONTRIBUTING.md`, and `tsconfig.tools.json` describe the current
  directly executable TypeScript boundary.

## 2026-09-05 - Workspace packages become erasable TypeScript with no build step

**Result**

- The six workspace packages (`plugin-sdk`, `manager`, `dsh-rc2-adapter`,
  `conversation-agent`, `github-read`, `github-review-publish`) are now
  `src/index.ts` sources that Node.js 24 executes directly through built-in
  type stripping (issue #20). Each package's `exports` points at the `.ts`
  file; the hand-written `index.d.ts` files are gone and their types live in
  the source next to the code they describe.
- Nothing about install, packaging, or release changed shape: there is still no
  `build`, `prepare`, or `prepack` script, `npm pack --ignore-scripts` ships
  the reviewed source (66 files, down from 72 without the declaration files),
  and the package-reproducibility check keeps its meaning. `npm run typecheck`
  (`tsc --noEmit`, TypeScript 6.0.3 pinned exactly) joins `npm test` in CI and
  in the release verify job.

**Why / context**

- The declaration files were a second description of each contract that could
  drift from the implementation with no test noticing; the exact-DSH consumer
  check compiled against the `.d.ts` surface, not the code. Folding the types
  into the source puts each public signature next to the implementation it
  describes, so both are reviewed together, and makes every internal validator
  visible to the compiler. The overload-above-implementation pattern still
  leaves overload/implementation agreement to the test suite rather than the
  compiler; what changed is that the two can no longer be edited apart.
- Upstream DSH ships `tsc` plus `tsdown` output under `lib/`; that layout was
  deliberately not adopted. A build output would put generated code between the
  reviewed source and the shipped tarball, which the reproducibility and
  reviewed-source release gates are built to exclude. Erasable syntax
  (`erasableSyntaxOnly`, `verbatimModuleSyntax`) keeps Node's stripping the
  only transform, so Node.js 24 is now a runtime requirement, not only a
  development one.
- The public signatures are carried verbatim from the old declaration files as
  overloads above each implementation, so the exported surface is reviewable
  line by line against the deleted `.d.ts`. The optional DSH peer packages the
  adapter binds its types to are not installed in this repository, so a minimal
  ambient fallback shipped with the adapter (`types/dsh-peer-fallbacks.d.ts`)
  lets `npm run typecheck` run standalone. An ambient declaration shadows the
  installed package in any program that includes it, so
  `npm run test:exact-dsh` compiles a separate program that excludes the
  fallback and maps the peer names to the pinned DSH checkout; that run remains
  the authority for the DSH-facing surface.
- Two consumer-facing consequences of shipping `.ts` came out of review and are
  now documented in the README: Node refuses to strip types under
  `node_modules`, so the packages load only from an unpacked artifact root; and
  a TypeScript consumer compiles the sources under its own options, so the
  sources are held to `noUncheckedIndexedAccess` and
  `exactOptionalPropertyTypes` as well, and a checked consumer fixture compiles
  them without the DSH peers in the repository contract test.
- This is the pilot for the same conversion in dsh-runtime-kit
  (sympoies/dsh-runtime-kit#202), which carries a hosted gate cycle this
  repository does not.

**Evidence**

- Zero specification edits: every existing test passes with only import-path
  changes, 94 pass / 0 fail / 1 environment-skip against the locked runtime-kit
  checkout on Node.js 24.16.0, and the same result on Node.js 26.
- `npm run test:exact-dsh` against the pinned DSH 0.1.1-rc.2 checkout: DSH's own
  `tsc` 6.0.3 resolves the `.ts` export targets and type-checks the adapter and
  its consumers strictly; the live agent tool round-trip passes.
- `tsc --declaration --emitDeclarationOnly` over the new sources, normalized for
  whitespace and the `declare` keyword, is identical to the deleted `.d.ts`
  files except that `EFFECTFUL_HOST_ACTION_CLASSES` is now declared (it was
  exported at runtime but never typed).
- Importing every package under Node.js 24.16.0 writes nothing to stderr; no
  `ExperimentalWarning` or stripping diagnostic appears in any test run.
- `git diff -M40%` pairs all six sources as renames (42% to 74% similarity; the
  smallest files gain the most type text relative to their size).

## 2026-09-01 - Conversation agent realizes the conversational profile

**Result**

- `packages/conversation-agent` (PR #19) implements the turn and reply
  contracts the `conversational` profile had been declaring against a plugin
  that no package provided, so the profile moves from a validated shape to a
  realizable contract.
- A turn may now carry channel context — `chatRef`, `senderRef`, `isGroup` —
  where the refs are opaque deployment-scoped digests, letting one agent serve
  group and direct chats on any channel without a real identifier entering the
  public repository.

**Why / context**

- The missing piece for a Telegram or LINE agent was never channel-specific:
  ingress and delivery are adapter-owned, so the reusable gap was the
  conversation contract itself.
- The profile had declared `conversation-agent >=1.0.0 <2.0.0`, which the
  coordinated 0.3.0 workspace version can never satisfy; the declaration had
  never been exercised because no package existed to check it against.

**Evidence**

- Independent review found five issues, all repaired before merge. Two were
  contract defects that testing alone had missed: a getter could pass the ref
  check and then substitute a raw chat id into the returned document,
  defeating the privacy guarantee; and text bounds counted UTF-8 bytes while
  the digest-pinned schemas declare `maxLength` in code points, so a 6000
  character CJK message satisfied the published contract yet was rejected at
  runtime.
- The keyed-digest requirement for refs is now normative in the schema field
  descriptions rather than README prose, so it travels with the digest-pinned
  contract; a bare hash of a numeric chat id is exhaustively invertible.
- 93 pass / 0 fail against the locked runtime-kit checkout, and
  `check-profile-compatibility` returns ok against a real git checkout at the
  locked revision, validating the recomputed profile, catalog, and lock digest
  chain.

**Follow-ups**

- The private deployment owns minting refs by HMAC over a deployment secret;
  an unsalted adapter would satisfy the shape while breaking the guarantee.
- `freezeClone` over caller-owned memory is shared with the other public
  packages, which carry no privacy claim today but would inherit the same
  substitution weakness if one were added.

## 2026-09-01 - Evaluate-before-build skill established; Telegram channel adopted

**Result**

- The `evaluate-dsh-plugin` skill (PR #17) now gates new capabilities on an
  ecosystem survey, fixed evaluation criteria, a throwaway-DSH_HOME probe
  (`scripts/dsh-plugin-probe.sh`), and a recorded adopt/reference/build
  decision under `docs/plugin-evaluations/`.
- Its first application decided the Telegram channel: adopt
  `@ashafizullah/dsh-telegram@0.5.1` (`docs/plugin-evaluations/telegram-channel.md`).

**Why / context**

- The DSH plugin ecosystem is large enough (13k+ GitHub `dsh-plugin` repos, a
  curated awesome list, thousands of npm packages) that building from scratch
  without a survey risks reinventing maintained work.
- The probe earns its keep: its fail-closed observation caught
  `dsh-telegram-multiagent` self-mounting **enabled** via its shipped patch
  layer after `dsh plugin add` silently bundle-registered it — exactly the
  class of supply-chain surprise the skill exists to surface before a real
  profile is touched.

**Evidence**

- Live probes against locked DSH 0.1.1-rc.2: two finalists PASS
  (fail-closed + disabled activation proven), two candidates FAIL on
  unresolvable prerelease peer ranges; owner test and full suite green on
  PR #17's repaired head.

**Links**

- PR #17 (skill + probe), `docs/plugin-evaluations/telegram-channel.md`
  (survey, probe transcripts summary, decision, follow-ups).

**Follow-ups**

- Public conversational Telegram profile composing the adopted plugin;
  private credential/ingress binding in the deployment repository; a future
  LINE record (no ecosystem candidate exists).
