# Development log - 2026-09

## 2026-09-01 - Conversation agent realizes the conversational profile

**Result**

- `packages/conversation-agent` (PR #19) implements the turn and reply
  contracts the `conversational` profile had been declaring against a plugin
  that no package provided, so the profile moves from a validated shape to a
  realizable contract.
- A turn may now carry channel context — `chatRef`, `senderRef`, `isGroup` —
  where the refs are opaque deployment-scoped digests, letting one agent serve
  group and direct chats on any channel without a real identifier entering the
  public repository.

**Why / context**

- The missing piece for a Telegram or LINE agent was never channel-specific:
  ingress and delivery are adapter-owned, so the reusable gap was the
  conversation contract itself.
- The profile had declared `conversation-agent >=1.0.0 <2.0.0`, which the
  coordinated 0.3.0 workspace version can never satisfy; the declaration had
  never been exercised because no package existed to check it against.

**Evidence**

- Independent review found five issues, all repaired before merge. Two were
  contract defects that testing alone had missed: a getter could pass the ref
  check and then substitute a raw chat id into the returned document,
  defeating the privacy guarantee; and text bounds counted UTF-8 bytes while
  the digest-pinned schemas declare `maxLength` in code points, so a 6000
  character CJK message satisfied the published contract yet was rejected at
  runtime.
- The keyed-digest requirement for refs is now normative in the schema field
  descriptions rather than README prose, so it travels with the digest-pinned
  contract; a bare hash of a numeric chat id is exhaustively invertible.
- 93 pass / 0 fail against the locked runtime-kit checkout, and
  `check-profile-compatibility` returns ok against a real git checkout at the
  locked revision, validating the recomputed profile, catalog, and lock digest
  chain.

**Follow-ups**

- The private deployment owns minting refs by HMAC over a deployment secret;
  an unsalted adapter would satisfy the shape while breaking the guarantee.
- `freezeClone` over caller-owned memory is shared with the other public
  packages, which carry no privacy claim today but would inherit the same
  substitution weakness if one were added.

## 2026-09-01 - Evaluate-before-build skill established; Telegram channel adopted

**Result**

- The `evaluate-dsh-plugin` skill (PR #17) now gates new capabilities on an
  ecosystem survey, fixed evaluation criteria, a throwaway-DSH_HOME probe
  (`scripts/dsh-plugin-probe.sh`), and a recorded adopt/reference/build
  decision under `docs/plugin-evaluations/`.
- Its first application decided the Telegram channel: adopt
  `@ashafizullah/dsh-telegram@0.5.1` (`docs/plugin-evaluations/telegram-channel.md`).

**Why / context**

- The DSH plugin ecosystem is large enough (13k+ GitHub `dsh-plugin` repos, a
  curated awesome list, thousands of npm packages) that building from scratch
  without a survey risks reinventing maintained work.
- The probe earns its keep: its fail-closed observation caught
  `dsh-telegram-multiagent` self-mounting **enabled** via its shipped patch
  layer after `dsh plugin add` silently bundle-registered it — exactly the
  class of supply-chain surprise the skill exists to surface before a real
  profile is touched.

**Evidence**

- Live probes against locked DSH 0.1.1-rc.2: two finalists PASS
  (fail-closed + disabled activation proven), two candidates FAIL on
  unresolvable prerelease peer ranges; owner test and full suite green on
  PR #17's repaired head.

**Links**

- PR #17 (skill + probe), `docs/plugin-evaluations/telegram-channel.md`
  (survey, probe transcripts summary, decision, follow-ups).

**Follow-ups**

- Public conversational Telegram profile composing the adopted plugin;
  private credential/ingress binding in the deployment repository; a future
  LINE record (no ecosystem candidate exists).
